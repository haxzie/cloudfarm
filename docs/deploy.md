# Deploying cloudfarm

Two Workers, both built from this repo by **Cloudflare Workers Builds**:

| Worker | Root directory | Build | Deploy |
| --- | --- | --- | --- |
| `cloudfarm-web` | `apps/web` | `pnpm run build:cf` | `npx wrangler deploy` |

`cloudfarm-api` is deployed by GitHub Actions, not Workers Builds — see below.

Workers Builds installs dependencies itself, so the build command is only the
build. `--prebuilt` makes the API deploy reuse the build output instead of
rebuilding the container image a second time. The web deploy can stay as plain
`wrangler deploy`: wrangler detects an OpenNext project and hands off to
`opennextjs-cloudflare deploy` on its own.

**The API does not deploy from Workers Builds.** Cloudflare's builders have no
Docker daemon, and the API's container image is built from
`apps/api/Dockerfile`, so the build dies in `verifyDockerInstalled` with
`run \`sudo systemctl start docker\``. GitHub's ubuntu runners do ship Docker,
so the API deploys from `.github/workflows/deploy-api.yml` instead. The web
Worker has no container and builds on Workers Builds fine.

That workflow needs two repository secrets: `CLOUDFLARE_API_TOKEN` (Edit
Workers template) and `CLOUDFLARE_ACCOUNT_ID`.

Leave the API's Workers Builds trigger disconnected, or every push logs a
failed build beside the successful Actions run.

### Always `pnpm run <script>`, never `pnpm <script>`

`deploy` and `build` are pnpm's own commands, and the built-in wins over a
script of the same name. `pnpm deploy` copies a workspace package into a
directory — it will not run the deploy script, and it fails confusingly. The
root `deploy:api` / `deploy:web` scripts spell out `run` for the same reason.

### Why two CLIs

`cf` reads `apps/api/cloudflare.config.ts`, which is where the Durable Objects,
the container and the bindings are declared. The web Worker is generated by
OpenNext instead: `opennextjs-cloudflare build` emits `.open-next/worker.js`
plus an assets directory, and its `deploy` wraps `wrangler deploy` with the
cache-population steps an OpenNext app needs.

`cf deploy` does not work in `apps/web`. It recognises Next, tries to configure
the project by shelling out to `@opennextjs/cloudflare migrate` through npm, and
dies on this workspace's `workspace:*` dependency protocol:

    npm error Unsupported URL Type "workspace:": workspace:*

So the split is forced by the tooling, not a preference. `apps/web` pins
`wrangler` to match OpenNext's `^4.148.0` peer requirement; without it the
hoisted 4.105.0 is picked up and is too old.

## One-time setup

### 1. Account resources

Already created:

- D1 `cloudfarm-db` — `cdfaf7a4-c3ec-475b-95ac-c485d545b7f8`, wired into
  `apps/api/cloudflare.config.ts`.
- R2 `cloudfarm-assets` — every bot's workspace lives under `bots/<id>/`.

### 2. API secrets

`cf secret put <NAME>` from `apps/api`, or the dashboard. None are in the repo.

| Secret | Where it comes from |
| --- | --- |
| `BETTER_AUTH_SECRET` | `openssl rand -base64 32` |
| `ANTHROPIC_API_KEY` | console.anthropic.com |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | the GitHub OAuth app below |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | an R2 API token with Object Read & Write |

The R2 pair is what the sandbox mount uses. Without it `exec` fails with
`source.endpoint must be a valid URL` — the shell is the only thing affected.

### 3. GitHub OAuth app

Sign-in is GitHub-only. Create an OAuth app whose callback is
`https://<api-host>/api/auth/callback/github`. The local app points at
`localhost:8787`, so production needs its own.

### 4. Database

    cd apps/api
    CLOUDFARM_D1_ID=cdfaf7a4-c3ec-475b-95ac-c485d545b7f8 pnpm db:migrate:remote

### 5. Connect the repo

In the dashboard, **Workers → Create → Connect Git**, once per Worker, using the
table at the top. This is the step that cannot be scripted: it mints a GitHub
App grant, and `cf builds workers create` requires a `--git-repository-grant-id`
that only that flow produces.

Set two build-time variables on `cloudfarm-web`:

- `NEXT_PUBLIC_API_URL` — the deployed API origin. Next inlines `NEXT_PUBLIC_*`
  at build time, so this must be a *build* variable; a runtime binding is never
  read.
- `NPM_FLAGS=--version` or equivalent is not needed; pnpm is detected from
  `packageManager` in the root `package.json`.

### 6. Cross-origin settings

The two Workers are different origins, so after the first deploy set on the API:

Both live in `apps/api/cloudflare.config.ts` as `bindings.text(...)` and point
at the custom domains:

- `WEB_URL` — `https://cloudfarm.dev`
- `BETTER_AUTH_URL` — `https://api.cloudfarm.dev`

`.dev.vars` overrides them with localhost for local development.

## Domains

| Host | Worker |
| --- | --- |
| `cloudfarm.dev`, `www.cloudfarm.dev` | `cloudfarm-web` |
| `api.cloudfarm.dev` | `cloudfarm-api` |

Declared as custom-domain routes in each Worker's config, so Cloudflare creates
the DNS records on deploy. The API gets a subdomain of the same apex rather
than a `workers.dev` host so the Better Auth session cookie is set on a
`cloudfarm.dev` origin.

**GitHub OAuth callback:** `https://api.cloudfarm.dev/api/auth/callback/github`

## Deploying by hand

    pnpm --filter api deploy     # needs Docker running locally
    pnpm --filter web deploy

## Notes

- Containers require a **Workers Paid** plan.
- Dropping `defineContainer` from `apps/api/cloudflare.config.ts` removes the
  Docker requirement entirely, at the cost of the bot's `exec` tool.
